## G01 已确认：BLE A 在线时插入 USB B

Owner 原话：
> 自动切换到设备B，同时BLE断开和设备A的连接，就是坚决杜绝出现之后的这种上传错了等奇奇怪怪的问题，就按照只连接的键盘来跑

解释：以单一活动键盘为原则；切到 USB B 时断开 A 的 BLE 链路，不保留可被后台写入的 A。所有读写必须属于当前目标及连接代次，旧任务和迟到回调不得转发给 B。原问题中提出的保留 A 草稿，不等于允许将其加载后自动保存给 B；具体草稿呈现仍待讨论。

G01 确认正常切换；图片上传场景由 G02 补充。保存/烧录等其他操作不据此一概假定任意中断安全。

## G02 已确认：图片上传 A 过程中插入 USB B

已向 Owner 提问：停止给 A 发送后续内容，结束旧任务并断开 A，再切到 B；此次上传显示“已中止”，结果无法确认则如实提示；保留本地图片，绝不向 B 自动续传；清理等待有时间上限，不让界面卡死。

Owner 选择：按这个顺序中止并切到 B（推荐）。

实施边界：隔离旧连接代次及迟到ACK；不发后续分片/COMMIT，不把已经提交但回执未知伪装成回滚成功。具体超时值和取消能力由实现证据确定；无需 Owner 决定底层线程细节。

## G03 已确认：USB 拔出后的行为

Owner 选择：拔 USB 就保持断开，由用户重新选择。
不自动查找 B 的 BLE，也不自动回到 A；状态轮询、Hook 等后台路径不得绕开未连接状态重建连接。重新插入 USB 的主动连接动作仍按 G01 和后续启动/目标规则区分。

## G04 已确认：启动软件时不自动连接

Owner 选择：启动后都保持未连接，由用户选择。
即使存在唯一 USB 或已保存 BLE，也不在启动、轮询、Hook 或后台身份读取时自动连接。仅启动桥进程不等于授权连接键盘。
G01 仍为已连接 A 后新插 USB B 的明确切换规则；未连接状态下新插 USB 的行为需另外澄清，不能拿 G04 或 G01 互相覆盖。

## G05 方向确认：主界面一键连接、桥后台运行

Owner 原话：
> 这块我其实希望做到就是当前系统蓝牙连接的蓝牙设备，然后蓝牙桥会跟随这个软件一起启动，然后自动连接开头为这个AhaKey的设备，自动连接，然后用户不需要单独打开这个蓝牙桥，它就只在这个软件界面点连接就可以了，你可以理解我的意思吗？我们可以再讨论

产品方向：桥随软件后台启动；用户只在主界面点击连接，不操作独立桥窗口；从系统当前已连接且名称以 AhaKey 开头的蓝牙设备中找目标。撤回“每次必须弹统一设备选择窗口”的建议，唯一符合条件目标应直接连接。
与 G04 的当前合并解释：软件启动只启动桥，点击连接才启动目标连接。此解释已向 Owner 明说；未将最新回答视为撤销 G04 的启动不自动连规则。
“当前系统已连接”与“仅已配对/附近可扫描”不能混为一谈。名称仅筛候选，具体设备与可用服务需技术核验，不能靠名称把任意设备视作键盘或沿用旧 MAC。
待确认：同时有多把符合条件目标时是否在主软件中请求选择；没有匹配项时的提示与刷新；USB与BLE同时可用时主按钮如何选目标。尚未实现或测试系统枚举/GATT兼容性。

## G12 已确认：拨杆草稿不替代图上的已保存配置

## G13 已确认：关闭主窗口隐藏到托盘，通过菜单退出

Owner 选择：× 隐藏到托盘，通过菜单退出。
不采纳“× 真正退出”的建议。主窗口右上角 × 隐藏到托盘，保留后台运行；菜单“退出程序”才是实际退出入口。此前“点击 × 无法退出”的反馈不能继续当成将 × 改为实际退出的授权。
图片上传中隐藏窗口是否继续上传、菜单退出时如何中止及限时清理，继续由 G14 对齐；固件烧录退出保护不因本选择而撤销。本轮仅记录需求，未修改生产代码。

## G14 已确认：图片上传、隐藏、取消与退出分开

Owner 选择：按这套规则处理（推荐）。
图片上传时点 × 隐藏到托盘，上传继续。上传界面提供“取消上传”，取消后软件仍可操作。点菜单“退出程序”则中止上传，限时清理后退出，不一直等待上传完成。取消或退出不承诺撤回已经写入键盘的内容。
本规则针对图片上传，不能推广成允许直接终止固件擦写；切换设备时仍按 G02 隔离旧任务，不向新目标续传。

## G15 已确认：模拟按键立即执行当前编辑内容

Owner 选择：保持点击后立即执行。
不采纳增加 3 秒倒计时的建议。点击“模拟按键”立即执行当前编辑类型及内容：快捷键执行当前快捷键，宏执行当前完整宏，不读取残留的旧快捷键替代宏，也不要求先保存到设备。
本选择未授权自动切换到其他窗口；模拟输入的目标遵循系统焦点。实现应按当前动作快照执行并保证本次模拟按下的键得到释放，不能把发送请求直接宣称为目标应用已成功执行。

## G16 已确认：切换目标只断开旧设备的软件配置通信

Owner 选择：只断开软件与 A 的通信（推荐）。
补充 G01 的“断开 BLE A”含义：结束 A 的上位机配置会话和旧任务，后续软件只读写 B；保留 A 在 Windows 中的蓝牙连接及打字功能。不取消系统配对，不主动断开 Windows 的键盘 HID 连接。
实现仍需验证配置 GATT 会话释放与系统 HID 共存；不得以仅关闭 UI 或清空显示来冒充旧任务已隔离。

## G17 已确认：审批含义由当前位置已保存绑定决定

Owner 选择：只有明确绑定自动批准才启用（推荐）。
只有当前实际位置已保存且已确认的绑定为“自动批准”时，才启用自动批准；自定义快捷键、自定义宏、无动作或配置未知时不得按物理上拨自动批准。其他情况保留平台自身审批，不再弹 AhaKey 自有确认窗。
G11/G12 的图文与实际审批判断必须使用一致的设备事实，未保存草稿不能改变审批权限。需要核对 Hook 与对外状态接口的消费者，不能只改 DeviceStatus 文案或主界面。此项是已确认产品语义，协议/架构影响仍需按 CHANGE 评审，不在 Grill 中实现。

## G18 已确认：意外 BLE 掉线后保持断开

Owner 选择：保持断开，点击连接后恢复（推荐）。
休眠、超出距离或桥异常导致 BLE 会话断开后，主软件保持未连接，提示用户重新点击“连接设备”；旧上传停止，不自动重连同一目标或其他目标，不自动续传。
下一次主动连接按当前设备候选与 USB 优先规则执行，不锁死旧 MAC。桥进程存活或恢复不等于授权自动连接键盘；后台轮询和 Hook 不得绕过此规则。短时单次请求超时不直接等同已确认掉线，故障判定由实现证据确定。

## G19 已确认：多 USB 候选由用户选择

软件未连接时，点击“连接设备”发现多把 USB 键盘，在主软件列出 USB 候选供选择；取消则保持未连接，不任意连接第一把，不自动转连蓝牙。只有一把 USB 时沿用 G07 直接连接。
已连接 A 后新插入一把 USB B，仍沿用 G01 自动切到 B；不得用多候选选择逻辑撤销该规则。候选身份必须能区分真实设备，连接前复核目标仍存在，不拿显示名称充当唯一标识。
