## 原范围缺陷

1. 读回四键/K1后Canvas与Inspector应同步，无需用户编辑触发刷新；设备读回不得把草稿标为未保存。
2. BLE K1长响应缺尾：先减小受支持协议内的BLE读片并验证完整响应、关联nonce/模式/offset/CRC；不假称已确认固件责任。只读超时不得被误归为永久写入隔离，但旧会话/迟到回包必须作废，保持手动重新连接。任何可能改变设备的请求失败继续保留原不确定保护，不重试未知写入。
3. 图片上传仍依据原A09/A10：实际数据分片写入、整体有界取消、退出、设备切换、桥卡住/慢回应必须离线故障注入。未实际测过的性能不能填Owner PASS/FAIL或保证某个吞吐率；没有证据不擅改画质、帧数、协议或重试策略。

## Hook管理新增修复（J014）

- 管理窗口打开/刷新只展示检测结果，不再自动弹模态更新催促；用户显式点安装/更新。按钮运行中有状态，结束明确成功或失败并重检，不出现无反馈或成功后永远待更新。
- 状态检测与实际生成版本、脚本及对应工具实际配置一致；更新后同版重检稳定为最新，缺文件/注册丢失/实际不兼容不能以单一版本戳冒充可用。
- Claude使用其正式settings.json Hook入口；Kimi以本机真实消费实现及官方配置为据解析正确配置根，不能继续把TOML写到无消费的hooks.json。未确认支持的Kimi版本明确显示不支持/不能确认，不假安装；禁止改第三方应用源码或自行安装依赖。
- 应用存在检测不能仅依赖安装器自己创建的空目录；区分已检测启动入口、只有配置痕迹、未检测应用。对缺软件或能力不足给明确说明，不返回假成功。
- 只更新AhaKey自身脚本及注册条目，保留用户和其他工具Hook/配置。备份后写入，失败可回溯；卸载若涉及同一入口，也不能删整个第三方hooks节点。诊断与测试使用隔离目录，不直接更新Owner真实Hook。
- 审批语义沿G17：仅明确AUTO才放行，其余走平台原生审批，禁止新增自有ask/deny或弹窗。

## Cursor多任务等待状态新增调查与修正（J015）

本次Owner授权覆盖原Contract第6节及TECHNICAL_BOUNDARIES里“Cursor灯色暂缓”的限制，仅限修复实际运行/等待状态的识别和会话归属。

- 正在等待批准对应WAITING，使用现有等待灯光配置（默认黄）；不能把所有preToolUse、工具运行缓慢或没有后续事件推断为等待批准。
- 各会话状态必须精确匹配已绑定slot，A等待不得改变B正在运行；批准/拒绝/执行结束后依据真实事件退出等待。
- 以当前平台官方能力及本机真实事件/状态证据为准。如缺可信等待信号，先报告能力缺口及需要Owner决定的产品方案，不能为了显示黄灯人为阻塞工具、额外触发审批或伪造状态。
- 不修改Firmware灯光协议，不强行覆盖用户自定义颜色。
