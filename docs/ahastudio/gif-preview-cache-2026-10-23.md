# GIF小屏预览重复解码修复

对应总WBS L02/Q04，原高CPU回归。基线b487465，现场安装0.2.3/build367（db7e410）。

## 现场与复现

仅在客户端虚拟键盘选Claude、选中LCD，不进入编辑，不切实体模式或上传素材。内置claude_0.gif有120帧。前台首分钟Studio单核CPU约19.165%；重新激活后的20秒独立样本21.237%，超过本次诊断用10%阈值。该阈值用于反馈，不冒充用户正式性能预算。非活动窗口的20秒样本0.8%及空闲调用栈不能用来宣称动画播放通过。

主动播放时5秒采样调用栈显示AnimatedGIFLayerView.image(at:)反复进入CGImageSourceCreateThumbnailAtIndex及GIF解码。旧16MiB缓存容不下固定320像素的完整120帧循环。按实际Retina显示区解码后，连同行跨度约16.15MiB，仍略超过旧预算。

首次计划十分钟采样在约一分钟后因固定Agent PID失效而停止，不计通过。Agent从51636变成36851；launchctl显示当前进程运行、该加载周期runs=1/无已退出状态。现有证据不能证明是GIF导致或属于崩溃，单列未解释的进程更换，不自动重启或修改Agent配置。语音日志仅新增权限快照，未发现该时段录音开始事件。

## 改动边界

- GIFPreviewFrames统一拥有源、解码及帧缓存，实际播放器直接调用。
- 按resizeAspect的实际视口和屏幕backing scale计算缩略帧，仍受原320/1200上限约束；不降低实际显示所需像素，不改变帧数、播放帧率和源文件。
- 每播放器NSCache成本上限改为32MiB，让当前完整LCD循环可复用。它是系统可驱逐的缓存成本配置，不是全App或严格RSS上限；大预览仍受限，不无限预解码全文件。
- 布局与屏幕倍率变化才更新解码尺寸并清旧帧；零尺寸过渡保持既有缓存，换源或失效源不显示旧素材。
- BLE、设备OLED素材、Voice、审批策略、用户草稿不变。

## 验证要求

最终测试在临时恢复旧固定尺寸/16MiB行为时必须失败，并在修复后验证：120帧第二轮复用、实际像素、缩放/Retina变更、重复/零布局、换源/坏源、源文件不变，以及真实NSView接线。再做完整回归、双轴审查、签名候选及相同前台性能对照。只有本地动画测试通过不能关闭设备OLED、长时、休眠或全部性能矩阵。
