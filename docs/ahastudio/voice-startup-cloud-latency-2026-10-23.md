# 首次语音响应与云端整理延迟

范围：VOICE-LAT-01、I02b、L02/Q04。用户在build365反馈首个按键无响应，后续两次短按集中执行、漏掉中间语音，云端整理等待过久。本次要求覆盖此前“首次HUD延迟暂缓”的决定，重启验收先暂停；F5仍暂缓。

## 已取得的证据

- 本机事件日志中，F18短按已到达客户端，约2秒后才出现录音启动；第二次短按与启动/停止落在同一秒，随后为空或识别错误。日志只有秒级时间，不能凭它把全部耗时精确归因到某个系统调用。
- 同一次测试的两段云端处理分别约38秒、26秒。较早一段因下一录音已开始，按现有隔离规则保留到待复制区，没有自动写进下一段。
- 旧实现将识别器创建、音频设备准备/启动和首次HUD等工作放在MainActor，键事件也交给该线程；云端请求上限为120秒。
- 使用一条固定合成文本对同一已配置服务做一次诊断，HTTP200/业务200，约3.74秒成功；未发送录音或个人文本，不输出账号、令牌、配额或处理后的文案。这不能证明服务始终快速，也不能称为修复服务端延迟。

## 行为合同

1. 首次触发立即发布“正在启动麦克风”状态。音频/识别初始化、停止和清理使用独立串行队列。HUD视图在启动时隐藏准备，不打开麦克风。
2. 短按保持开始/停止语义。启动中再次按键表示取消，界面立即响应；过期启动完成后必须清理，不能复活录音或覆盖新会话。长按在准备完成前松开，也取消该次启动。
3. 只有音频真正就绪后显示“录音中”。麦克风硬件的实际冷启动仍可能需要时间，不能承诺按下瞬间就有音频；准备提示明确要求就绪后说话。
4. 停止监听取消未完成的启动；更改语音绑定前同样视启动为忙碌。旧录音的停止完成/结果回调仍按generation隔离。
5. 云端正常结果继续使用；一次处理最多等待8秒，包括连接和完整响应。超时取消本地传输，保留原始转写，并以“已写入原文／云端整理超时”提示。不会自动重试。客户端取消不保证服务端停止已开始的计算或退还用量。
6. 每段录音独立保有识别累积器、按下时策略和结束任务。开始下一段时，上一段尚在结束的识别继续完成，迟到的完整文字进入待复制区，不粘贴到新录音或覆盖新HUD。旧账号超时不能覆盖新登录状态。音频线程只传递不可变识别快照。
7. 保留现有按模式策略、短长按策略快照、F18绑定、麦克风选择及权限；不为提速删除主动重复词，不改此前停顿前后句保留算法。
