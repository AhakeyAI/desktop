# Codex 验收归因与优化设计 SOP

状态：生效

日期：2026-09-16

适用范围：客户端、Runtime、Studio、Hook、安装发布、统一固件、HIL 与 WBS 资格门禁

## 1. 目的

验收不再止于“指出哪一行错了”。每次 Codex 验收都必须同时回答：

1. 证据是否满足任务卡；
2. 失败为什么发生；
3. 为什么原测试或原分解没有更早发现；
4. 下一轮应做最小补丁、重写测试 oracle，还是先冻结新设计；
5. 哪些已经通过的部分必须保持不动。

本 SOP 吸收近期客户端 C5IR 系列和固件 B/BR 系列的有效做法：固定审查范围、双轴审查、生产路径实证、突变验证、同类反复失败时先产出详细设计，再恢复实施。

## 2. 每轮验收步骤

### 2.1 固定审查对象

- 写明任务卡 ID、基线、终点、`lastReviewedCommit`、允许路径和实际 diff。
- 区分本轮增量、既有 dirty、历史 accepted 面与未执行门禁。
- 不用后续一次绿色结果覆盖本轮已出现的真实失败。

### 2.2 独立证据复核

- Standards 与 Spec 分轴检查；每条 finding 标 `P0/P1/P2/P3`。
- 至少复核任务卡点名的生产路径、测试 oracle 和 fail-closed 负向路径。
- 对“门禁会抓回归”的声明，优先要求红测试、忠实 mutant 或故障注入；只看绿测不等于证明门禁有牙。
- HIL、签名、安装、刷机等现实门禁不能被 mock/host test 替代。

### 2.3 归因诊断

每个阻塞 finding 必须给出四层归因：

| 层次 | 必答问题 |
|---|---|
| 直接触发点 | 哪个输入、状态、调用序列或环境条件导致失败？ |
| 系统性根因 | 是局部实现错误，还是接口、表示法、状态机、任务分解、测试 oracle 或环境隔离错误？ |
| 漏检原因 | 旧测试为何仍绿；是否只测镜像、未走生产路径、组合维度不完整或负向谓词过宽？ |
| 影响面 | 哪些模块、固件族、数据、发布门禁和既有 accepted 结论受影响？ |

根因至少归入一类：

- `implementation`：孤立实现/边界错误；
- `contract`：接口、协议、ABI、状态含义不一致；
- `representation`：表示法或模块形状无法覆盖问题空间；
- `oracle`：测试镜像、断言或突变门禁不能证明生产行为；
- `environment`：工具链、签名、worktree、设备或权限错误被当成产品结论；
- `decomposition`：WBS/任务卡把互相依赖的风险错误拆开或混在一起；
- `integration`：单模块正确但生产接线、生命周期或跨进程顺序错误；
- `hardware-reality`：只有真机、电源、USB/BLE、EEPROM/Flash 现实才能裁决。

### 2.4 选择收敛路径

Codex 必须明确选择且只选择一种主路径：

1. `accepted`：证据闭合；记录残余 P2/P3 和是否另开卡。
2. `mechanical-rework`：表示法/接口/oracle 正确，只修有限缺陷；给精确白名单、保留项、红测试和完成定义。
3. `diagnosis-design-checkpoint`：暂停产品补丁，先产出并验收设计文档。
4. `reslice`：原任务边界错误，拆成新的依赖切片。
5. `blocked/user-gate`：缺真实权限、设备、产品裁决或外部状态。

以下任一成立即进入 `diagnosis-design-checkpoint`，不得继续补丁堆叠：

- 同一语义轴连续两轮验收不通过；
- 新 finding 是上一轮修复的相邻组合或同一状态空间遗漏；
- 需要改变公共接口、持久布局、恢复状态机或所有权模型；
- 测试与生产不是同一实现/接线，无法仅靠补 case 建立证明；
- 负向测试可能因环境失败而假绿；
- 三个以上模块共同维护一个没有单一 owner 的不变量；
- 原完成定义无法区分真成功和假成功。

## 3. 诊断设计检查点的完成定义

设计文档至少包含：

1. 失败时间线与最小复现；
2. 已接受事实、被推翻假设与证据链接；
3. 有限状态/输入维度与不变量；
4. 推荐的深模块接口与唯一事实源；
5. 两个以上方案及不采用理由；
6. 生产调用链、数据/恢复迁移和兼容边界；
7. 失败前缀、重启/重试/取消/断连状态表；
8. 永久红测试、组合矩阵、mutation/fault-injection 方案；
9. 已验收用例向新测试的迁移表，防止重构丢证据；
10. 实现路径白名单、明确禁止项、RAM/Flash/性能/签名预算；
11. 后续 WBS 切片、依赖和每片退出条件；
12. HIL/USER-GATE 的现实步骤与停止条件。

终版设计由 Codex 冻结。执行方可以提交事实审计或设计草稿；Codex 必须给出明确的 accepted 版本或精确修订，不能把尚未裁决的开放问题直接塞回实现卡。

## 4. WBS 拆解规则

- 有明显状态空间、持久恢复、跨进程/跨传输、协议兼容或安全门禁的工作，默认先设 `A: diagnosis/design`，再设 `B: core/representation`、`C: production wiring/migration`、`D: integration/HIL`；简单机械项可省略不需要的阶段。
- 每张实现卡在开工前写明“关键不变量、风险轴、允许机械返工边界、设计升级触发器”。
- 同一风险轴的返工编号连续计数，不能换卡名清零。
- Codex 每轮验收维护“已通过并冻结的面”；下一轮只开放未闭合面。
- 设计改变原任务范围时，先更新 WBS 依赖与任务卡，再开工；board 口头说明不构成授权。
- 产品核心未证明前，不开放 HIL/签名/安装/刷机；host 证明也不得冒充 HIL 完成。

## 5. 强制反馈模板

以下模板适用于 accepted、退回、阻塞和重新切片。无适用内容时写“无 + 原因”，不得删节。

```text
### Codex 验收：<任务卡/轮次> — <accepted | mechanical-rework | diagnosis-design-checkpoint | reslice | blocked>

审查冻结
- range：<base...head>
- lastReviewedCommit：<sha>
- 白名单/实际 diff：<结果>
- 独立复跑：<命令、轮数、结果>

裁决
- Standards：<P0/P1/P2/P3 汇总>
- Spec：<P0/P1/P2/P3 汇总>
- 结论：<一句话>

归因诊断
- 直接触发点：<可复现输入/状态/序列>
- 系统性根因：<分类 + 解释>
- 旧门禁漏检原因：<为什么以前会绿>
- 影响面：<模块/数据/设备/版本>
- 已通过并冻结：<下一轮禁止重做的部分>

优化方案设计
- 选择路径：<accepted / mechanical / design checkpoint / reslice / blocked>
- 推荐结构：<接口、状态机、唯一事实源或最小机械改动>
- 不采用方案：<至少写明主要替代方案及原因；机械项可写无>
- 永久证明：<红测试、矩阵、mutant、故障注入、HIL>
- 兼容/迁移/资源影响：<结论>

下一轮可执行返工单
- 目标：<单一目标>
- 允许路径：<精确白名单>
- 禁止项：<保留边界>
- 完成定义：<可判定的测试与证据>
- 依赖/USER-GATE：<条件>
- 后续状态：<任务卡/queue/WBS 如何更新>

残余风险与后续优化
- P2/P3：<列表或无>
- 是否另开卡：<是/否 + 理由>
```

## 6. 反馈质量门

以下反馈不得推动任务状态：

- 只有 finding，没有根因与下一轮设计；
- 只说“补测试”，没有说明测试为何能杀死旧实现；
- 用测试镜像证明生产路径；
- 未固定审查范围或未记录 `lastReviewedCommit`；
- 把同类第三轮补丁伪装成新任务以绕过设计检查点；
- 退回时没有列出已通过并冻结部分；
- accepted 时没有说明残余风险，或把未跑的 HIL 写成通过。
