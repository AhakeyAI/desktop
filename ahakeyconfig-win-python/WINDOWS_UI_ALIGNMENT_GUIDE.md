# Windows UI Alignment Guide

本文档用于将 macOS 端已经落地的 4 个交互能力对齐到 Windows 端，供同事直接实现、批注和对齐使用。

适用范围：
- 首次打开应用时的功能引导
- 页面内问号说明
- 语音输入按钮右侧的状态显示
- 语音输入悬浮窗

本文档目标：
- 让 Windows 同事不需要额外口头说明，就能知道应该做什么
- 让后续 AI 或开发同事可以快速定位到 macOS 已实现的位置
- 统一文案、交互和状态定义

## 对齐范围总览

Windows 端需要对齐以下 4 项能力：

1. 首次启动功能引导
2. 问号说明按钮
3. 语音输入按钮右侧状态显示
4. 语音输入悬浮窗

其中第 3、4 项和语音体验直接相关：
- 请 Windows 端在界面右侧的“启动语音输入”按钮旁，同步加入语音状态显示
- 右侧状态显示用于提供常驻状态反馈
- 悬浮窗用于在录音、识别、粘贴等关键阶段给用户即时反馈
- 用户既可以通过主界面状态知道整体可用性，也可以通过悬浮窗感知当前正在发生什么

## 一、首次启动功能引导

### 1. 产品目标

首次打开应用时，不直接把所有复杂功能暴露给用户，而是用一个轻量引导弹窗告诉用户：

- 先从哪里开始
- “启动语音”是做什么的
- “连接设备和配置按键”是做什么的

这个弹窗只自动出现一次，避免反复打扰。后续如果用户想再看，可以手动从菜单中打开。

### 2. 触发时机

- 主窗口第一次显示后触发
- 不是应用构造时立刻弹出，而是在窗口展示后延迟约 `700ms`
- 弹窗关闭后，紧接着进入缺失 Hook 的检查流程

### 3. 只显示一次的规则

通过本地配置保存展示状态：

- `ui/welcome_guide_seen`
- `ui/welcome_guide_version`

当前 macOS 使用的版本标记为：

```text
{APP_VERSION}-guide-5
```

含义：
- 如果引导文案或结构发生变化，可以通过提升 `guide` 版本号让旧用户再次看到一次新引导
- 如果版本号不变，则已经看过的用户不会再次自动弹出

### 4. 弹窗标题与内容

窗口标题：

```text
欢迎使用 Vibecoding Keyboard
```

副标题：

```text
你可以先从下面两个功能开始：
```

卡片 1 标题：

```text
启动语音
```

卡片 1 文案：

```text
点击顶部“启动语音输入”，可以把说话内容快速转换成文字。
首次使用时，系统会提示你开启麦克风、输入监控和辅助功能权限。
当右侧状态变成绿色“语音已就绪”后，就可以按下 Caps 键开始录音。
```

卡片 2 标题：

```text
连接设备和配置按键
```

卡片 2 文案：

```text
点击顶部“连接”，连接键盘设备后就可以查看设备状态。
进入“模式配置”页，可以为每个按键设置功能，并把配置保存到设备。
如果需要灯效或动图显示，可以在“动画管理”里添加图片或 GIF。
```

底部提示：

```text
建议第一次使用时，先体验“启动语音”，再连接设备配置按键。
```

确认按钮：

```text
我知道了
```

### 5. 交互要求

- 弹窗为模态弹窗
- 不需要复杂分页
- 不需要“上一步 / 下一步”
- 只要用户明确看完并点击“我知道了”即可

### 6. Windows 端建议保持一致的点

- 标题和两张卡片结构保持一致
- 文案尽量一致
- 自动弹出一次 + 菜单里允许再次打开
- 如果 Windows 端没有完全相同的 Hook 机制，可以保留引导结构，但将 Hook 相关后置逻辑按 Windows 自己的流程处理

### 7. macOS 代码位置

- 弹窗类：`vibe_code_config_tool-master/src/ui/main_window.py`
  - `WelcomeGuideDialog`
- 卡片构造：
  - `vibe_code_config_tool-master/src/ui/main_window.py`
  - `_build_feature_card()`
- 自动触发：
  - `vibe_code_config_tool-master/src/ui/main_window.py`
  - `showEvent()`
  - `_run_startup_guidance_flow()`
  - `_maybe_show_welcome_guide()`
  - `_show_welcome_guide()`
- 配置持久化：
  - `vibe_code_config_tool-master/src/ui/main_window.py`
  - `_WELCOME_GUIDE_VERSION`
  - `QSettings` 下的 `ui/welcome_guide_seen` / `ui/welcome_guide_version`
- 菜单入口：
  - `vibe_code_config_tool-master/src/ui/main_window.py`
  - “查看功能引导”

## 二、问号说明按钮

### 1. 产品目标

对于不适合在主界面展开解释、但用户第一次使用又容易困惑的功能，在标题旁加一个小问号按钮。

用户点击问号后，弹出一个轻量说明框，说明：

- 这个功能是干什么的
- 适合什么场景

### 2. 统一交互定义

问号按钮形态：

- 显示为一个圆形 `?`
- 大小较小，不抢主界面注意力
- 鼠标悬停时有轻微高亮
- 点击后弹出一个标准信息弹窗

交互要求：

- 不要跳转页面
- 不要打开浏览器
- 不要做复杂的浮层交互
- 以“短说明 + 使用场景”为主

### 3. 当前需要对齐的 3 个问号

#### 3.1 AhaType

位置：
- 顶部连接栏中，“启动AhaType”按钮右侧

标题：

```text
AhaType 说明
```

正文：

```text
AhaType 会把语音识别结果再做一次整理和润色。

适合用于口语转书面语、补全标点，或让输入内容更适合直接发送和记录。

使用前需要先登录，并且云端服务可用。
```

#### 3.2 按键映射

位置：
- “模式配置”页中，“按键映射”标题右侧

适合用来设置常用快捷键、组合键、文本输入，或不同模式下的专用布局。

#### 3.3 动画管理

- “模式配置”页中，“动画管理”标题右侧

### 4. Windows 端对齐建议

- 三个问号按钮的位置与各自功能标题对齐
- 文案保持一致
- 如果 Windows 端 UI 控件体系不同，允许表现形式略有差异
- 但必须保留“点击即显示说明”的低成本交互

## 三、语音输入按钮右侧状态显示

### 1. 产品目标

在“启动语音输入”按钮右侧直接显示当前语音状态，让用户不依赖额外弹窗或悬浮窗，也能立刻知道：

- 语音是否已启动
- 当前是否在录音
- 当前是否正在识别
- 当前是否可继续使用
- 是否出现权限问题或异常

这是一个非常关键的可视反馈能力，Windows 端需要补齐。

### 2. 布局位置

在顶部连接栏中，按钮顺序如下：

```text
连接 -> 启动语音输入 / 停止语音输入 -> 状态灯 -> 状态文字 -> 启动AhaType
```

也就是说：
- “启动语音输入”按钮后面，紧跟一个小圆点状态灯
- 状态灯后面紧跟一段状态文字

### 3. 状态灯表现

#### 3.1 停止状态

- 灰色空心圆
- 文案：`语音未启动`

#### 3.2 启动中 / 关闭中 / 处理中

- 灰色圆环底
- 橙色弧线旋转
- 属于“正在变化中的过渡态”

对应状态：
- `starting`
- `stopping`
- `processing`

#### 3.3 录音中

- 红色实心圆
- 文案：`录音中`

#### 3.4 已就绪

- 绿色实心圆
- 文案：`语音已就绪`

#### 3.5 异常

- 红色实心圆
- 文案：`语音异常` 或更具体的错误说明

### 4. 状态文字定义

默认状态文案如下：

| 状态值 | 默认文案 |
| --- | --- |
| `stopped` | `语音未启动` |
| `starting` | `语音启动中` |
| `recording` | `录音中` |
| `processing` | `处理中` |
| `ready` | `语音已就绪` |
| `stopping` | `语音关闭中` |
| `error` | `语音异常` |

实际运行时，允许使用更细的业务文案覆盖默认文案，例如：

- `模型检查完成`
- `模型加载中`
- `模型已加载，正在启动服务`
- `服务已启动，等待客户端连接`
- `按键监听已启动`
- `本地识别中`
- `AhaType 整理中`
- `准备粘贴`
- `需要麦克风权限`
- `请开启系统权限`
- `需要辅助功能权限`
- `语音启动异常`
- `语音服务异常`

### 5. 按钮文字联动

按钮文字需要和语音是否运行联动：

- 未运行：`启动语音输入`
- 运行中：`停止语音输入`

### 6. 状态切换建议

Windows 端建议尽量和 macOS 保持相同语义：

#### 启动阶段

- 用户点击“启动语音输入”
- 状态进入：`语音启动中`
- 后续根据语音引擎实际进度更新为：
  - `模型检查完成`
  - `模型加载中`
  - `模型已加载，正在启动服务`
  - `服务已启动，等待客户端连接`
  - `按键监听已启动`
  - 最终变为 `语音已就绪`

#### 使用阶段

- 按住录音：`录音中`
- 松开开始识别：`本地识别中`
- 如有文本整理：`AhaType 整理中`
- 识别结果回写前：`准备粘贴`
- 完成后回到：`语音已就绪`

#### 权限 / 异常阶段

- 麦克风没开：`需要麦克风权限`
- 输入监控 / 辅助功能未开：`请开启系统权限` 或 `需要辅助功能权限`
- 模块缺失 / 启动失败：`语音启动异常`
- 进程异常退出：`语音服务异常`

### 7. 对 Windows 同事的明确实现要求

请 Windows 端加入此功能，不要只保留原来的悬浮方式。

最低要求如下：

1. 在“启动语音输入”按钮旁加入状态灯和状态文字
2. 支持至少以下状态：
   - 未启动
   - 启动中
   - 录音中
   - 处理中
   - 已就绪
   - 异常
3. 按钮文字在“启动语音输入 / 停止语音输入”之间切换
4. 当语音真正可用时，必须明确显示 `语音已就绪`

如果 Windows 端已有悬浮窗：
- 可以保留悬浮窗
- 但仍建议新增这一组内嵌状态显示

### 8. macOS 代码位置

- 状态灯组件：
  - `vibe_code_config_tool-master/src/ui/widgets/connection_bar.py`

- 顶部栏布局：

## 四、语音输入悬浮窗

### 1. 产品目标

悬浮窗用于在用户录音和识别的关键时刻，提供一个不依赖主窗口聚焦状态的即时反馈层。

它的定位不是替代主界面右侧状态显示，而是补充：

- 主界面右侧状态显示：负责常驻、稳定、可回看的状态
- 悬浮窗：负责即时、短时、阶段性的反馈

建议 Windows 端也加入此能力。

### 2. 显示位置

macOS 当前实现中，悬浮窗显示在：

- 当前屏幕的中下方
- 水平居中
- 距离底部约 `84px`

表现特点：

- 无边框
- 半透明深色背景
- 圆角
- 始终置顶
- 不接受鼠标输入
- 不抢主焦点

### 3. 内容结构

悬浮窗内部由两部分组成：

1. 左侧状态图形
2. 右侧状态文字

状态图形规则：

- `starting` / `processing`：橙色旋转弧线
- `recording`：红色实心圆
- `ready`：绿色实心圆
- `error`：红色实心圆

### 4. 主要状态与文案

悬浮窗当前使用的主要文案包括：

```text
语音启动中
请求麦克风权限
请允许麦克风访问
检查系统权限
请先完成系统授权
等待语音服务
语音已就绪
录音中
本地识别中
AhaType整理中
准备粘贴
需要辅助功能权限
复制失败
粘贴失败
语音结果接收异常
语音服务连接异常
```

说明：

- 这些文案不要求 Windows 端逐字完全一致
- 但建议语义保持一致
- 尤其是录音中、识别中、准备粘贴、异常提示这些核心阶段，应明确反馈

### 5. 自动隐藏规则

悬浮窗不是永久显示的。

当前 macOS 规则：

- `ready`：短暂显示后自动隐藏，约 `1400ms`
- `准备粘贴` 等成功收尾阶段：约 `1200ms`
- `error`：约 `2600ms`
- `recording` / `processing`：通常保持可见，直到状态进入下一阶段
- 明确收到 `hide` 命令时立即隐藏

Windows 端建议保持同类逻辑：

- 成功结束类状态短暂显示后自动消失
- 录音中、处理中等进行中状态保持显示
- 错误状态显示时间略长一点，给用户足够反应时间

### 6. 触发时机建议

Windows 端建议在以下时机展示悬浮窗：

#### 启动阶段

- 点击“启动语音输入”后显示 `语音启动中`
- 请求麦克风权限时显示 `请求麦克风权限`
- 等待语音服务就绪时显示 `等待语音服务`
- 服务准备完成后显示 `语音已就绪`

#### 使用阶段

- 开始录音时显示 `录音中`
- 松开进入识别时显示 `本地识别中`
- 进入云端整理时显示 `AhaType整理中`
- 写入前显示 `准备粘贴`

#### 异常阶段

- 麦克风权限缺失
- 系统权限缺失
- 辅助功能权限缺失
- 粘贴失败 / 复制失败
- 语音服务异常

### 7. 与右侧状态显示的关系

Windows 端请不要把悬浮窗理解成“有了就不用右侧状态条”。

推荐关系如下：

- 主界面右侧状态显示：始终存在，用于展示当前总体状态
- 悬浮窗：只在关键阶段出现，用于给用户即时反馈

例如：

- 用户点击启动语音后
  - 右侧状态：`语音启动中`
  - 悬浮窗：`语音启动中`
- 用户正在录音
  - 右侧状态：`录音中`
  - 悬浮窗：`录音中`
- 识别完成并准备回到空闲
  - 右侧状态：最终回到 `语音已就绪`
  - 悬浮窗：短暂显示 `语音已就绪` 后自动消失

### 8. 对 Windows 同事的明确实现要求

建议 Windows 端一并加入悬浮窗，不要只做按钮右侧状态文字。

最低要求如下：

1. 悬浮窗为一个独立的轻量反馈层
2. 不抢焦点，不阻挡用户继续输入
3. 支持至少这些阶段：
   - 启动中
   - 录音中
   - 处理中
   - 已就绪
   - 异常
4. 成功与错误状态支持自动隐藏
5. 与右侧状态显示同步，但不互相替代

### 9. macOS 代码位置

- 悬浮窗本体：
  - `vibe_code_config_tool-master/capswriter/voice_hud.py`
  - `VoiceHud`

- 悬浮窗启停与消息发送：
  - `vibe_code_config_tool-master/capswriter/core_client_mac.py`
  - `_voice_hud_enabled()`
  - `_start_voice_hud()`
  - `_set_voice_hud()`
  - `_hide_voice_hud()`
  - `_stop_voice_hud()`

- 默认开关：
  - `CAPSWRITER_ENABLE_HUD`
  - 未显式关闭时，默认启用

- 当前实现方式：
  - 悬浮窗作为独立子进程运行
  - 通过 `stdin` 接收 JSON 行命令
  - 主语音客户端在不同阶段向悬浮窗发送状态和文案

## 六、验收标准

Windows 端实现完成后，至少应满足以下验收要求：

1. 第一次打开应用会自动弹出功能引导
2. 引导关闭后不再反复弹出
3. 用户可以通过菜单再次打开引导
4. `AhaType`、`按键映射`、`动画管理` 都有问号说明
5. 问号说明点击即可查看，不需要跳转其他页面
6. “启动语音输入”按钮右侧有状态灯和状态文字
7. 语音启动后，用户能看到从“启动中”到“已就绪”的过程
8. 录音、识别、异常状态都有明确反馈
9. 有独立悬浮窗用于展示关键阶段即时反馈
10. 悬浮窗不会抢焦点，不会阻挡用户继续输入
11. 悬浮窗与右侧状态显示语义一致
